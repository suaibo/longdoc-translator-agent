# LongDoc Translator Agent 架构设计

版本：v0.1  
状态：MVP 架构设计稿  
适用范围：论文翻译模式

---

## 1. 架构目标

LongDoc Translator Agent 的 MVP 目标是完成一个可演示、可恢复、可观察的长文档翻译 Agent 工作流。

架构设计重点：

- 长任务可分阶段执行。
- 术语确认作为 Human-in-the-Loop 中断点。
- 每个 chunk 翻译完成后写入检查点。
- 前端通过轮询查看任务状态和进度。
- 文档解析、Agent 编排、翻译、导出相互解耦。
- MVP 只支持单任务队列，避免并发复杂度。

## 2. 系统分层

```text
React + Vite Web 控制台
        |
        v
FastAPI API 层
        |
        v
应用服务层 / Domain Services
        |
        v
LangGraph Agent 工作流层
        |
        v
SQLite + 文件存储 + OpenAI-compatible LLM + Docling
```

### 2.1 Web 控制台

职责：

- 上传文档。
- 展示任务列表和任务详情。
- 展示术语表确认页面。
- 展示翻译进度和 chunk 状态。
- 展示结果下载入口。

页面：

- 上传页
- 任务列表页
- 任务详情页
- 术语表确认页
- 翻译进度页
- 结果下载页

### 2.2 FastAPI API 层

职责：

- 暴露 REST API。
- 参数校验。
- 文件上传处理。
- 调用应用服务。
- 返回统一 JSON 响应。
- 对输出文件提供下载。

### 2.3 应用服务层

核心服务：

- `JobService`：创建任务、查询任务、状态流转、取消和恢复。
- `ParserService`：调用 Docling，将 PDF / MD / TXT 转换为统一 Markdown。
- `ChunkService`：按章节和段落切分文档，生成 chunk。
- `TermService`：抽取术语、保存术语、处理用户确认译名。
- `TranslationService`：调用 LLM 翻译 chunk，维护术语和上下文。
- `CheckpointService`：保存与读取检查点，支持失败续跑。
- `OutputService`：生成双语 Markdown、纯中文 Markdown、翻译报告。
- `MetricService`：记录 token、耗时、失败次数、重试次数。

### 2.4 Agent 工作流层

使用 LangGraph 编排长任务节点。

工作流节点：

```text
parse_document
-> split_sections
-> extract_terms
-> interrupt_for_term_review
-> translate_chunk
-> summarize_chunk_context
-> mark_risks
-> generate_outputs
-> generate_report
```

说明：

- `interrupt_for_term_review` 是 MVP 的唯一人工中断点。
- `translate_chunk` 按 chunk 顺序执行。
- 每个 chunk 完成后写入数据库和检查点。
- 失败时任务进入 `FAILED`，保留已完成结果。

### 2.5 持久化层

使用 SQLite 保存结构化数据，使用本地文件系统保存上传文件、解析结果和导出结果。

## 4. 存储目录约定

```text
storage/
  uploads/
    {jobId}/
      original.pdf
  parsed/
    {jobId}/
      document.md
  outputs/
    {jobId}/
      bilingual.md
      translated.md
      report.md
```

规则：

- 上传文件保存到 `storage/uploads/{jobId}/`。
- Docling 解析后的 Markdown 保存为 `storage/parsed/{jobId}/document.md`。
- 导出文件保存到 `storage/outputs/{jobId}/`。
- 数据库只保存文件路径，不保存大段二进制文件。

## 5. 任务状态机

```text
UPLOADED
  -> PARSED
  -> WAITING_TERM_REVIEW
  -> TRANSLATING
  -> COMPLETED
```

异常状态：

```text
FAILED
CANCELLED
```

状态说明：

- `UPLOADED`：文件已上传，等待解析。
- `PARSED`：文档已解析并完成切分。
- `WAITING_TERM_REVIEW`：术语表已抽取，等待用户确认。
- `TRANSLATING`：正在分块翻译。
- `COMPLETED`：翻译完成，输出文件已生成。
- `FAILED`：任务失败，可尝试恢复。
- `CANCELLED`：任务取消，不再继续执行。

## 6. 核心工作流

### 6.1 创建任务

```text
前端上传文件
-> FastAPI 保存原始文件
-> 创建 translation_job
-> 后台 worker 开始执行 parse_document
```

创建成功后，前端拿到 `jobId` 并进入任务详情页。

### 6.2 解析与切分

```text
parse_document
-> Docling 解析 PDF / MD / TXT
-> 生成 document.md
-> split_sections 按标题和段落切 chunk
-> 写入 document_chunk
```

### 6.3 术语抽取与确认

```text
extract_terms
-> LLM 抽取术语和建议译名
-> 写入 term_entry
-> 任务状态变为 WAITING_TERM_REVIEW
-> 前端展示术语确认页
```

用户确认术语后：

```text
PUT /api/jobs/{jobId}/terms
-> 保存 confirmed_translation
-> 任务状态变为 TRANSLATING
-> 后台 worker 继续翻译
```

### 6.4 分块翻译

每个 chunk 翻译时携带：

- 用户确认术语表
- 当前章节标题
- 当前章节摘要
- 上一个 chunk 摘要
- 当前 chunk 原文

执行后：

- 写入 chunk 译文。
- 更新 chunk 状态。
- 写入 checkpoint。
- 更新任务进度。
- 记录 token 和耗时。

### 6.5 输出生成

所有 chunk 完成后：

```text
generate_outputs
-> bilingual.md
-> translated.md
-> report.md
-> 任务状态变为 COMPLETED
```

## 7. 前后端交互逻辑

### 7.1 上传阶段

1. 前端调用 `POST /api/jobs` 上传文件。
2. 后端返回 `jobId`。
3. 前端跳转任务详情页。
4. 前端每 2 秒轮询 `GET /api/jobs/{jobId}`。

### 7.2 术语确认阶段

1. 任务状态变为 `WAITING_TERM_REVIEW`。
2. 前端调用 `GET /api/jobs/{jobId}/terms`。
3. 用户编辑术语译名。
4. 前端调用 `PUT /api/jobs/{jobId}/terms`。
5. 后端保存术语并继续翻译。

### 7.3 翻译阶段

1. 前端继续轮询任务详情。
2. 前端调用 `GET /api/jobs/{jobId}/chunks` 展示 chunk 进度。
3. 任务失败时展示错误和恢复按钮。
4. 用户点击恢复后调用 `POST /api/jobs/{jobId}/resume`。

### 7.4 完成阶段

1. 任务状态变为 `COMPLETED`。
2. 前端展示三个下载入口。
3. 用户分别下载双语译文、纯中文译文和报告。

---

## 8. 单任务队列策略

MVP 一次只允许一个任务处于运行中状态。

运行中状态包括：

- `UPLOADED`
- `PARSED`
- `WAITING_TERM_REVIEW`
- `TRANSLATING`

当存在运行中任务时，再次创建任务返回 `40902`。

---

## 9. 异常处理策略

### 9.1 Docling 解析失败

- 任务状态变为 `FAILED`。
- 错误码：`50002`。
- 保存错误信息。
- 不自动切换解析器。

### 9.2 LLM 调用失败

- 当前 chunk 标记为 `FAILED`。
- 任务状态变为 `FAILED`。
- 已完成 chunk 保留。
- 用户可调用 `resume` 继续。

### 9.3 用户取消任务

- 任务状态变为 `CANCELLED`。
- 后台 worker 检查到取消状态后停止后续 chunk。
- 已生成的中间结果保留。

## 11. Parser 与版面标准化

解析层统一输出 `ParsedBlock[]`，每个 block 至少保留：

- `blockId`、`kind`、`text`、`markdown`、`order`
- PDF 的 `pageNo` 和 bbox（含页面宽高）
- 标题级别、Docling 原始标签和版面调整元数据
- `TABLE / FORMULA / REFERENCE / STRUCTURE / LONG_PARAGRAPH / PARSER_WARNING` 风险

输入适配规则：

- PDF：固定使用 Docling `DocumentConverter`，OCR 支持 `auto / off / force`。
- Markdown：标题、段落、列表、围栏代码、块公式和 Markdown 表格转换为结构块。
- TXT：按空行形成段落块，随后进入相同标准化流程。

### 11.1 论文解析总原则

论文、硕博学位论文和技术报告不能只按纯文本顺序处理。Parser 必须先保留版面结构，再由 Layout Normalizer 修正阅读顺序，最后由 Chunk Service 决定翻译粒度。

固定原则：

- 标题、正文、列表、表格、公式、图片、caption、页眉和页脚先识别为独立结构块。
- 解析阶段不直接按字符数切割 PDF 文本，避免破坏栏顺序、表格行列和公式边界。
- 自动修正必须保留原始页码、bbox、Docling 标签和调整记录，方便报告追踪与人工复核。
- 无法可靠判断的内容优先保留原文并标记风险，不静默删除或猜测重建。
- Parser 负责生成和标准化 `ParsedBlock[]`；Chunk Service 负责在不破坏结构的前提下组合或拆分翻译 chunk。

### 11.2 双栏阅读顺序修正

论文常见的双栏页面在 PDF 文本流中可能出现“左一、右一、左二、右二”的交错顺序。标准化策略如下：

1. 按页聚合带 bbox 的 block。
2. 根据 block 宽度、横向中心和左右区域的纵向重叠判断是否存在双栏。
3. 同一双栏区域按“左栏从上到下，再右栏从上到下”重排。
4. 跨越大部分页面宽度的标题、摘要标题、表格、图片和公式视为分段边界，边界前后分别判断栏结构。
5. 不带 bbox 或栏归属不明确的 block 保留原始相对顺序。
6. 被自动重排的 block 写入 `layoutAdjusted=true`，并标记 `STRUCTURE` 风险。

目标不是还原原 PDF 的视觉排版，而是恢复适合连续阅读和翻译的语义顺序。

### 11.3 页眉页脚过滤

页眉、页脚、页码、学校名称、期刊名称和章节短标题可能在每页重复，不能进入术语抽取和正文翻译。

过滤分两层：

- 强规则：Docling 明确标记为 `page_header` 或 `page_footer` 的 block 直接从正文流移除。
- 重复规则：位于页面顶部或底部、规范化文本相同、且出现在至少两页或半数页面中的内容视为重复版面元素。

保护规则：

- 只按“出现页数”计数，不能因为同一页出现两次就判定为跨页重复。
- 正文区域的重复术语、章节标题和表格内容不能用该规则删除。
- 无法确定是正文还是页眉页脚时保留内容，并标记 `PARSER_WARNING`。

### 11.4 表格原子性

表格是结构块，不是若干普通文本行。Parser 阶段必须保持表格原子性：

- 一个小表格对应一个 `TABLE` block，保存完整 Markdown、caption、表头、数据行、页码和 bbox。
- 不在 Parser 阶段把表格按行混入相邻正文，也不允许通用段落切分器从表格中间截断。
- 表格前后的 caption、注释和来源说明通过元数据与表格关联，不能被当作无关段落移动到其他章节。
- 合并单元格、跨页表格、列错位或识别置信度不足时保留 Docling 结果，并标记 `TABLE` 和 `PARSER_WARNING` 风险。
- MVP 保证结构尽量保留和风险可见，不承诺重建任意复杂表格的视觉版式。

### 11.5 大表分组

当完整表格超过 Chunk Service 的 token 或行数阈值时，才允许按数据行分组。拆分规则如下：

1. caption、列头和表格注释先从数据行中独立识别。
2. 只在完整数据行之间切分，不拆单元格，不把一行切到两个 chunk。
3. 每个分组重复列头，使分组可以独立交给 LLM 理解和翻译。
4. 每个分组重复 caption；首组使用原 caption，后续组增加“续表”语义标记，例如 `Table 2 (continued)`，避免被误认为新表。
5. 表尾注释和来源说明默认放在最后一组；若注释约束所有分组，则通过上下文元数据注入每组，但输出时只渲染一次。
6. 所有分组共享 `tableGroupId`，并记录 `groupIndex`、`groupCount` 和原表 block ID。
7. 翻译完成后按分组顺序重新合并，输出阶段去除为了上下文而重复的 caption/header，只保留正确的连续表格结构。

小表默认整体翻译。只有大表确实超过阈值时才分组，不能为了追求统一而把所有表格机械拆散。

### 11.6 Caption 与 Header 重复处理

这里的重复分为两类，处理方式不同：

- 页面级重复：期刊页眉、论文短标题、页码等属于噪声，按页眉页脚规则过滤。
- 表格分组重复：caption 和列 header 是为了让大表分组保持上下文而主动复制，属于结构元数据，必须保留到翻译请求中。

实现约束：

- 主动复制的 caption/header 标记 `syntheticRepeat=true`，不作为新的术语抽取语料，不单独生成译文段落。
- 输出合并时根据 `tableGroupId` 去重；caption 只输出一次，列 header 按最终 Markdown 表格结构决定是否重复。
- 图 caption 与图片 block 保持邻接和关联；不跨章节移动，也不因文本相同而按页眉规则删除。
- caption 无法确定归属时保留原位置，并标记 `STRUCTURE` 风险。

### 11.7 公式与引用风险

公式和引用优先保持原样，不让通用翻译逻辑改写其结构。

公式处理：

- Docling `formula`、Markdown `$...$`、`$$...$$`、`\(...\)` 和 `\[...\]` 识别为公式内容。
- 行间公式作为独立 `FORMULA` block；行内公式保留在所属段落中。
- 公式符号、LaTeX、编号和交叉引用不翻译，只翻译公式周围的解释文本。
- 公式缺失、括号不闭合、编号错位或 OCR 后符号可疑时标记 `FORMULA` 风险。

引用处理：

- `[1]`、`[2-5]`、`(Smith, 2020)` 等引用标记保留原样。
- 参考文献条目可识别为 `REFERENCE` block，不能与正文段落交错重排。
- 引用密集、编号疑似丢失、作者年份格式异常或 OCR 混淆时标记 `REFERENCE` 风险。
- MVP 不自动校验引用是否真实存在，只检查解析后的结构完整性和明显异常。

### 11.8 OCR 与解析错误标记

OCR 是 PDF Parser 的解析选项，不作为独立业务主线：

- `auto`：优先使用 PDF 内置文本，需要时启用 OCR。
- `off`：关闭 OCR，适合文本型 PDF。
- `force`：整页 OCR，适合扫描版论文。

错误分级：

- 局部可恢复：乱码、异常空白、重复字符、低置信度文本、bbox 缺失、疑似漏字等保留原文，并在 block 上标记 `PARSER_WARNING`；若与版面顺序有关，同时标记 `STRUCTURE`。
- 结构可恢复：表格、公式或引用局部解析异常时保留对应 block，并叠加 `TABLE / FORMULA / REFERENCE` 风险。
- 文档不可恢复：PDF 损坏、加密无法读取、Docling pipeline 失败或无法生成有效 block 时，任务进入 `FAILED`，错误码使用 `50002`。

风险项至少记录：

- `jobId`、`blockId` 或后续生成的 `chunkId`
- 风险类型和严重级别
- 页码、bbox 和原文摘录
- 自动处理动作，例如“已重排双栏”或“已过滤重复页眉”
- 建议人工检查的信息

所有风险最终汇总到 `report.md`。自动修正不等于无风险，发生过结构调整的内容仍应可追踪。

### 11.9 Parser 与 Chunk Service 边界

Parser 输出结构化、已排序的 `ParsedBlock[]`，但不负责按照 LLM token 上限完成最终切块。

Chunk Service 必须遵守：

- 普通段落可按句边界拆分，不能截断单词、公式或引用标记。
- 标题与其后的正文保持章节归属。
- 小表、独立公式和短 caption 作为原子块处理。
- 大表只能按 11.5 的规则分组。
- block 上的风险和版面元数据必须传递到 chunk、数据库风险项和最终报告。

## 12. Chunk Service

Chunk Service 位于 Parser 与后续 LangGraph/Translation Service 之间，输入为已排序的 `ParsedBlock[]`，输出为可持久化的 `ChunkDraft[]` 和 `document_chunk` 记录。

### 12.1 切块策略

- 标题开启新的章节上下文，并与其后的正文保持相同 `sectionTitle`。
- 普通段落按配置的 token 阈值合并；超长段落只在句子边界拆分。
- 行内公式和引用标记在句子拆分前使用占位保护，不能从中间断开。
- 独立公式、代码和图片作为原子 chunk，即使超过建议阈值也不机械截断。
- 小表和关联 caption 保持一个 `TABLE` chunk。
- 大表按完整数据行分组，每组重复表头；后续组 caption 增加 `(continued)`，并标记 `syntheticRepeat=true`。

配置项：

```text
CHUNK_MAX_TOKENS=1800
TABLE_MAX_ROWS=20
```

当前 token 数为本地启发式估算：CJK 字符按一个 token 估算，其他非空白字符约每四个计一个 token。该数值用于切块预算，不作为真实模型计费数据。

### 12.2 结构元数据

`document_chunk` 除原文外保存：

- `chunkType`：`TEXT / TABLE / FORMULA / PICTURE / CODE`
- `sourceBlockIds`：来源 ParsedBlock ID 列表
- `structureMetadata`：页面、bbox、block 类型和表格分组信息
- `tokenEstimate`：本地 token 估算
- `hasRisk / riskSummary`：聚合后的风险信息

表格分组元数据包括：

```text
tableGroupId
groupIndex
groupCount
originalTableBlockId
caption
headerRows
syntheticRepeat
```

PDF caption 优先根据 Docling `caption_refs` 与 `self_ref` 关联；无法获得引用时，使用紧邻表格或图片的 caption 作为 fallback。

### 12.3 幂等与状态边界

- chunk ID 由 `jobId + chunkIndex` 稳定生成，重复执行不会新增重复记录。
- 只允许对 `UPLOADED / PARSED` 任务执行切块。
- 只允许重建 `PENDING` chunk；任何已进入翻译、完成、失败或跳过状态的 chunk 都拒绝覆盖。
- 重切后删除多余的旧 `PENDING` chunk，并重新生成对应风险项。
- 切块成功后任务进入 `PARSED`，`currentStage=split_sections`，并更新 chunk 总数。
- 整个 chunk、风险和任务状态更新在同一业务数据库事务中完成。

### 12.4 风险继承

ParsedBlock 风险去重后写入 chunk，并生成关联的 `risk_item`。风险元数据包含来源 block、页面、bbox 和表格分组信息，供后续报告与人工检查使用。

表格即使 Parser 未提前附加风险，Chunk Service 也会确保存在 `TABLE` 风险，避免绕过版面标准化时丢失提示。

### 12.5 当前限制

- Chunk Service 当前尚未由后台 Worker 或 LangGraph 自动调用。
- Docling 未提供 caption 引用且 caption 不相邻时，只能保留原顺序并等待风险检查。
- 跨页合并单元格和非 Markdown 规则表格不做猜测性重建。
- 当前增量迁移只支持新增 SQLite 列；字段重命名、删除和复杂数据迁移后续使用 Alembic。
