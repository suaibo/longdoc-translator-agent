# LongDoc Translator Agent 架构设计

版本：v0.1  
状态：MVP 架构设计稿  
适用范围：论文翻译模式

---

## 1. 架构目标

LongDoc Translator Agent 的 MVP 目标是完成一个可演示、可恢复、可观察的长文档翻译 Agent 工作流。

架构设计重点：

- 长任务可分阶段执行。
- 术语确认作为 Human-in-the-Loop 中断点。
- 每个 chunk 翻译完成后写入检查点。
- 前端通过轮询查看任务状态和进度。
- 文档解析、Agent 编排、翻译、导出相互解耦。
- MVP 只支持单任务队列，避免并发复杂度。

## 2. 系统分层

```text
React + Vite Web 控制台
        |
        v
FastAPI API 层
        |
        v
应用服务层 / Domain Services
        |
        v
LangGraph Agent 工作流层
        |
        v
SQLite + 文件存储 + OpenAI-compatible LLM + Docling
```

### 2.1 Web 控制台

职责：

- 上传文档。
- 展示任务列表和任务详情。
- 展示术语表确认页面。
- 展示翻译进度和 chunk 状态。
- 展示结果下载入口。

页面：

- 上传页
- 任务列表页
- 任务详情页
- 术语表确认页
- 翻译进度页
- 结果下载页

### 2.2 FastAPI API 层

职责：

- 暴露 REST API。
- 参数校验。
- 文件上传处理。
- 调用应用服务。
- 返回统一 JSON 响应。
- 对输出文件提供下载。

### 2.3 应用服务层

核心服务：

- `JobService`：创建任务、查询任务、状态流转、取消和恢复。
- `ParserService`：调用 Docling，将 PDF / MD / TXT 转换为统一 Markdown。
- `ChunkService`：按章节和段落切分文档，生成 chunk。
- `TermService`：抽取术语、保存术语、处理用户确认译名。
- `TranslationService`：调用 LLM 翻译 chunk，维护术语和上下文。
- `CheckpointService`：保存与读取检查点，支持失败续跑。
- `OutputService`：生成双语 Markdown、纯中文 Markdown、翻译报告。
- `MetricService`：记录 token、耗时、失败次数、重试次数。

### 2.4 Agent 工作流层

使用 LangGraph 编排长任务节点。

工作流节点：

```text
parse_document
-> split_sections
-> extract_terms
-> interrupt_for_term_review
-> translate_chunk
-> summarize_chunk_context
-> mark_risks
-> generate_outputs
-> generate_report
```

说明：

- `interrupt_for_term_review` 是 MVP 的唯一人工中断点。
- `translate_chunk` 按 chunk 顺序执行。
- 每个 chunk 完成后写入数据库和检查点。
- 失败时任务进入 `FAILED`，保留已完成结果。

### 2.5 持久化层

使用 SQLite 保存结构化数据，使用本地文件系统保存上传文件、解析结果和导出结果。

## 3. 存储目录约定

```text
storage/
  uploads/
    {jobId}/
      original.pdf
  parsed/
    {jobId}/
      document.md
  outputs/
    {jobId}/
      bilingual.md
      translated.md
      report.md
```

规则：

- 上传文件保存到 `storage/uploads/{jobId}/`。
- Docling 解析后的 Markdown 保存为 `storage/parsed/{jobId}/document.md`。
- 导出文件保存到 `storage/outputs/{jobId}/`。
- 数据库只保存文件路径，不保存大段二进制文件。

## 4. 任务状态机

```text
UPLOADED
  -> PARSED
  -> WAITING_TERM_REVIEW
  -> TRANSLATING
  -> COMPLETED
```

异常状态：

```text
FAILED
CANCELLED
```

状态说明：

- `UPLOADED`：文件已上传，等待解析。
- `PARSED`：文档已解析并完成切分。
- `WAITING_TERM_REVIEW`：术语表已抽取，等待用户确认。
- `TRANSLATING`：正在分块翻译。
- `COMPLETED`：翻译完成，输出文件已生成。
- `FAILED`：任务失败，可尝试恢复。
- `CANCELLED`：任务取消，不再继续执行。

## 5. 核心工作流

### 5.1 创建任务

```text
前端上传文件
-> FastAPI 保存原始文件
-> 创建 translation_job
-> 后台 worker 开始执行 parse_document
```

创建成功后，前端拿到 `jobId` 并进入任务详情页。

### 5.2 解析与切分

```text
parse_document
-> Docling 解析 PDF / MD / TXT
-> 生成 document.md
-> split_sections 按标题和段落切 chunk
-> 写入 document_chunk
```

### 5.3 术语抽取与确认

```text
extract_terms
-> LLM 抽取术语和建议译名
-> 写入 term_entry
-> 任务状态变为 WAITING_TERM_REVIEW
-> 前端展示术语确认页
```

用户确认术语后：

```text
PUT /api/jobs/{jobId}/terms
-> 保存 confirmed_translation
-> 任务状态变为 TRANSLATING
-> 后台 worker 继续翻译
```

### 5.4 分块翻译

每个 chunk 翻译时携带：

- 用户确认术语表
- 当前章节标题
- 当前章节摘要
- 上一个 chunk 摘要
- 当前 chunk 原文

执行后：

- 写入 chunk 译文。
- 更新 chunk 状态。
- 写入 checkpoint。
- 更新任务进度。
- 记录 token 和耗时。

### 5.5 输出生成

所有 chunk 完成后：

```text
generate_outputs
-> bilingual.md
-> translated.md
-> report.md
-> 任务状态变为 COMPLETED
```

## 6. 前后端交互逻辑

### 6.1 上传阶段

1. 前端调用 `POST /api/jobs` 上传文件。
2. 后端返回 `jobId`。
3. 前端跳转任务详情页。
4. 前端每 2 秒轮询 `GET /api/jobs/{jobId}`。

### 6.2 术语确认阶段

1. 任务状态变为 `WAITING_TERM_REVIEW`。
2. 前端调用 `GET /api/jobs/{jobId}/terms`。
3. 用户编辑术语译名。
4. 前端调用 `PUT /api/jobs/{jobId}/terms`。
5. 后端保存术语并继续翻译。

### 6.3 翻译阶段

1. 前端继续轮询任务详情。
2. 前端调用 `GET /api/jobs/{jobId}/chunks` 展示 chunk 进度。
3. 任务失败时展示错误和恢复按钮。
4. 用户点击恢复后调用 `POST /api/jobs/{jobId}/resume`。

### 6.4 完成阶段

1. 任务状态变为 `COMPLETED`。
2. 前端展示三个下载入口。
3. 用户分别下载双语译文、纯中文译文和报告。

## 7. 单任务队列策略

MVP 一次只允许一个任务处于运行中状态。

运行中状态包括：

- `UPLOADED`
- `PARSED`
- `WAITING_TERM_REVIEW`
- `TRANSLATING`

当存在运行中任务时，再次创建任务返回 `40902`。

---

## 8. 异常处理策略

### 8.1 Docling 解析失败

- 任务状态变为 `FAILED`。
- 错误码：`50002`。
- 保存错误信息。
- 不自动切换解析器。

### 8.2 LLM 调用失败

- 当前 chunk 标记为 `FAILED`。
- 任务状态变为 `FAILED`。
- 已完成 chunk 保留。
- 用户可调用 `resume` 继续。

### 8.3 用户取消任务

- 任务状态变为 `CANCELLED`。
- 后台 worker 检查到取消状态后停止后续 chunk。
- 已生成的中间结果保留。

## 10. Parser 与版面标准化

解析层统一输出 `ParsedBlock[]`，每个 block 至少保留：

- `blockId`、`kind`、`text`、`markdown`、`order`
- PDF 的 `pageNo` 和 bbox（含页面宽高）
- 标题级别、Docling 原始标签和版面调整元数据
- `TABLE / FORMULA / REFERENCE / STRUCTURE / LONG_PARAGRAPH / PARSER_WARNING` 风险

输入适配规则：

- PDF：固定使用 Docling `DocumentConverter`，OCR 支持 `auto / off / force`。
- Markdown：标题、段落、列表、围栏代码、块公式和 Markdown 表格转换为结构块。
- TXT：按空行形成段落块，随后进入相同标准化流程。

版面标准化顺序：

1. 删除 Docling 明确标记的页眉页脚。
2. 对页面顶部或底部的重复文本按“出现页数”识别并过滤。
3. 根据 bbox 宽度和横向中心识别左右栏；同一版面段内按左栏从上到下、再右栏从上到下重排。
4. 全宽标题、表格、图片等作为双栏分段边界，避免跨越全宽元素错误重排。
5. 对发生双栏修正的 block 标记 `STRUCTURE` 风险，供报告和人工复核。

表格在 Parser 阶段保持为完整结构块，不按文本行拆散。小表整体进入后续 chunk；大表由 ChunkService 按行组切分，并在每组重复表头。
