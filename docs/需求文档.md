# LongDoc Translator Agent 需求文档

版本：v0.2
状态：MVP 需求稿  
项目定位：长文档结构化翻译 Agent

---

## 1. 项目定位

LongDoc Translator Agent 是一个面向长文档翻译的 Agent 工作流系统。

它的目标不是做普通翻译接口，而是解决长文档翻译中的工程问题：

- 长文档无法一次性放进上下文。
- 论文术语需要前后一致。
- PDF、表格、公式和标题结构容易在转换中丢失。
- 长任务容易中断，需要检查点和续跑。
- 高风险内容需要人工确认。
- 翻译结果需要可审查、可导出、可追踪。

MVP 阶段优先支持论文翻译模式，后续再扩展小说翻译模式。

---

## 2. 目标用户

主要用户：

- 需要阅读英文论文的学生
- 需要翻译硕博论文、技术报告的研究者
- 需要处理长篇英文资料的开发者
- 希望获得双语对照译文和术语表的人

后续用户：

- 长篇小说翻译者
- 网文 / 出版物译者
- 需要维护人物、地名和风格一致性的长文本创作者

---

## 3. MVP 范围

### 3.1 必须实现

- 上传 `PDF / Markdown / TXT` 文件。
- 使用 Docling 将文档解析为 `ParsedBlock[]`，生成调试用 Markdown，并在增强阶段持久化 DocumentIR Lite。
- 先按标题、表格、公式等结构硬边界切分，再在章节内部使用语义边界辅助和 token 上限兜底。
- 抽取术语表。
- 用户确认或编辑术语译名。
- 使用确认后的术语表进行分块翻译。
- 翻译时携带章节摘要和前一块摘要，形成滑动窗口记忆。
- 每个 chunk 完成后保存检查点。
- 失败后支持从最近完成的 chunk 续跑。
- 标记表格、公式、引用、OCR 和疑似结构风险片段，并保留原始页码、bbox 与资产。
- 导出双语 Markdown、纯中文 Markdown、翻译报告；输出增强阶段增加双语/中文 HTML、原始文件下载和结果资源包。
- Web 控制台展示任务进度、术语表、分块状态和下载入口。

### 3.2 MVP 暂不实现

- 用户登录和权限系统。
- 多用户隔离。
- 多任务并发。
- DOCX 导出。
- 完整 PDF 排版还原。
- 图片内容翻译。
- 对任意复杂或低置信度表格进行猜测性重建。
- 每章人工确认。
- 风险片段逐条人工确认。
- 小说模式完整实现。

## 4. 输入与输出

### 4.1 输入格式

MVP 支持：

- `.pdf`
- `.md`
- `.txt`

说明：

- PDF 默认使用 Docling 解析。
- Markdown 和 TXT 用于快速测试和调试。
- Docling 解析失败时，任务进入失败状态，不自动切换解析器。
- 原始上传文件始终保留；PDF 原文件允许完整下载，但不等同于翻译 PDF。

### 4.2 输出文件

基础输出：

1. `bilingual.md`
   - 原文和中文译文对照。
   - 作为可编辑、可搜索、可版本控制的交换格式。

2. `translated.md`
   - 纯中文译文。
   - 保留章节、公式、图片引用和可表达的表格结构。

3. `report.md`
   - 包含进度、术语表、风险片段、耗时和 token 统计。

MVP 输出增强：

4. `bilingual.html`
   - 面向用户直接阅读的双语版本。
   - 统一渲染表格、公式、图片和风险提示。

5. `translated.html`
   - 面向连续阅读的中文 HTML。

6. `result.zip`
   - 包含 Markdown、HTML、原始上传文件、manifest 和表格/公式/图片资产。

Markdown 不是复杂论文版式的唯一真相。简单表格使用 GFM；复杂但可信的表格使用 HTML；低置信度表格使用原始截图和可用的 CSV/JSON 附件。

## 5. Agent 工作流

MVP 工作流如下：

```text
parse_document
-> split_sections
-> extract_terms
-> interrupt_for_term_review
-> translate_chunk
-> summarize_chunk_context
-> mark_risks
-> generate_outputs
-> generate_report
```

### 5.1 parse_document

职责：

- 接收上传文件。
- 调用 Docling 解析文档。
- 输出标准化 `ParsedBlock[]`、调试用 Markdown，并为 DocumentIR Lite 提供结构数据和资产引用。

### 5.2 split_sections

职责：

- 根据标题层级建立 `sectionPath`。
- 标题、表格、公式、图片、代码和参考文献作为结构硬边界。
- 在同一章节内按段落形成候选单元，使用语义边界评分辅助合并。
- 使用 target / soft / hard token 预算兜底。
- 保存 `boundaryReason`、边界评分、来源 block 和章节路径。

当前已实现标题硬边界、句界拆分、原子块和单一 token 上限；标题栈、语义评分和三档预算属于下一阶段。

### 5.3 extract_terms

职责：

- 从全文或前若干章节中抽取专业术语。
- 为每个术语生成建议中文译名。
- 保存到术语表。

### 5.4 interrupt_for_term_review

职责：

- 暂停工作流。
- 等待用户在 Web 控制台确认或编辑术语表。
- 用户确认后继续翻译。

### 5.5 translate_chunk

职责：

- 按 chunk 顺序翻译。
- 翻译时携带已确认术语表、当前章节摘要、前一 chunk 摘要和当前 chunk 原文。

### 5.6 summarize_chunk_context

职责：

- 为已翻译 chunk 生成简短上下文摘要。
- 作为下一 chunk 的滑动窗口记忆。

### 5.7 mark_risks

职责：

- 标记表格、公式、引用、疑似结构复杂片段。
- 风险片段进入报告。
- MVP 不在此处中断人工审核。

### 5.8 generate_outputs

职责：

- 生成双语和中文 Markdown。
- 按结构类型选择 GFM、HTML table 或原始截图兜底。
- 输出增强阶段生成双语/中文 HTML、manifest 和 result.zip。
- 保留并提供原始上传文件下载。

### 5.9 generate_report

职责：

- 生成翻译报告。
- 汇总任务进度、术语表、风险片段、耗时、token 统计。

## 6. Web 控制台需求

MVP 不做登录，打开后直接进入控制台。

### 6.1 上传页

功能：

- 上传 PDF / MD / TXT。
- 翻译模式固定为 `paper`。
- PDF 可选择 `ocrMode=auto / off / force`，默认 `auto`；Markdown 和 TXT 不展示 OCR 选项。
- 创建翻译任务。

### 6.2 任务详情页

展示：

- 任务名称
- 当前状态
- 当前阶段
- 总 chunk 数
- 已完成 chunk 数
- 错误信息
- 创建时间

### 6.3 术语表确认页

展示：

- 原术语
- Agent 建议译名
- 用户确认译名

操作：

- 编辑译名
- 确认术语表
- 确认后启动翻译

### 6.4 翻译进度页

展示：

- chunk 列表
- 所属章节
- 翻译状态
- 是否有风险标记
- 当前进度百分比

操作：

- 取消任务
- 失败后继续任务

### 6.5 结果下载页

基础展示：

- 双语 Markdown 下载
- 纯中文 Markdown 下载
- 翻译报告下载

输出增强后优先展示：

- 双语 HTML
- 中文 HTML
- 原始上传文件
- `result.zip`

Markdown 标记为可编辑格式，HTML/结果包标记为推荐阅读格式。

## 7. REST API 需求

### 7.1 创建任务

```http
POST /api/jobs
```

请求：

- multipart 文件上传
- `mode=paper`

响应：

```json
{
  "jobId": "job_xxx"
}
```

### 7.2 查询任务列表

```http
GET /api/jobs
```

### 7.3 查询任务详情

```http
GET /api/jobs/{jobId}
```

返回任务状态、当前阶段、总 chunk 数、已完成 chunk 数和错误信息。

### 7.4 查询术语表

```http
GET /api/jobs/{jobId}/terms
```

### 7.5 确认术语表

```http
PUT /api/jobs/{jobId}/terms
```

用户提交编辑后的术语表。确认后，任务从 `WAITING_TERM_REVIEW` 进入 `TRANSLATING`。

### 7.6 查询分块

```http
GET /api/jobs/{jobId}/chunks
```

### 7.7 下载输出文件

```http
GET /api/jobs/{jobId}/outputs/{type}
```

基础 `type`：

- `bilingual`
- `translated`
- `report`

输出增强目标：

- `bilingual_html`
- `translated_html`
- `package`

原始文件使用独立的 `GET /api/jobs/{jobId}/source`。

### 7.8 继续任务

```http
POST /api/jobs/{jobId}/resume
```

用于从最近检查点恢复失败任务。

### 7.9 取消任务

```http
POST /api/jobs/{jobId}/cancel
```

## 8. 数据模型

### 8.1 translation_job

保存任务 ID、文件名、文件路径、模式、状态、当前阶段、总 chunk 数、已完成 chunk 数、错误信息、创建时间和更新时间。

### 8.2 document_chunk

保存 chunk ID、job ID、顺序号、章节标题、原文、译文、状态和风险标记。

### 8.3 term_entry

保存 term ID、job ID、原术语、Agent 建议译名、用户确认译名和是否确认。

### 8.4 agent_checkpoint

保存 checkpoint ID、job ID、LangGraph thread ID、当前节点、状态快照和创建时间。

### 8.5 translation_metric

保存 job ID、token 消耗、耗时、失败次数和重试次数。

---

## 9. 任务状态

```text
UPLOADED
PARSED
WAITING_TERM_REVIEW
TRANSLATING
COMPLETED
FAILED
CANCELLED
```

说明：

- `WAITING_TERM_REVIEW` 是 MVP 的 Human-in-the-Loop 中断状态。
- `FAILED` 状态必须保留已完成 chunk。
- `CANCELLED` 状态不再继续后台翻译。

---

## 10. 非功能需求

- 单任务队列：MVP 一次只运行一个翻译任务。
- 进度轮询：前端定时调用任务详情接口。
- 检查点：每个 chunk 翻译完成后写入 PostgreSQL。
- 可恢复：失败后可从最近完成 chunk 继续。
- 可观察：控制台能看到任务状态、阶段和 chunk 进度。
- 可导出：基础流程能下载三个 Markdown 文件；最终 MVP 质量验收增加 HTML 阅读文件、原始文件和结果包。
- 安全渲染：HTML 必须转义不可信文本并使用标签白名单，不执行源文档脚本。
- 安全打包：ZIP 和 manifest 中的路径必须规范化，禁止路径穿越和绝对路径。

---

## 11. 验收标准

MVP 验收：

- 上传 Markdown 论文片段后能完整跑通工作流。
- 上传 TXT 长文后能按段落分块翻译。
- 上传 PDF 后能通过 Docling 解析并进入同一流程。
- 术语表确认页可以编辑译名。
- 翻译结果使用用户确认术语。
- 翻译中断后可以继续。
- 简单表格可渲染为 GFM；复杂表格不会被强行降级为错误 pipe 表格，低置信度时保留原图并进入风险报告。
- 任务完成后能下载双语译文、纯中文译文、报告和原始文件；输出增强完成后可下载 HTML 与结果包。
- README 能说明项目定位、技术栈、Agent 工作流和后续模式。

## 14. 文档结构与输出质量要求

详细设计以 `docs/文档结构与输出策略.md` 为准。

固定产品判断：

- 当前 Chunk Service 是规则基线，不能在产品文案中称为完整语义切分。
- 结构硬边界不能被 embedding 或 token 压力覆盖。
- 语义评分不可用时必须回退到规则基线。
- Markdown 用于可编辑交换，HTML 用于直接阅读，原始文件用于追溯。
- PDF 原文件完整返回不代表已生成翻译 PDF。
- 低置信度表格和公式优先保留原始证据，不猜测性生成看似整齐但错误的结构。
